# AlarmControl 규칙 안내

[English](RULES_GUIDE.md) | **한국어**

AlarmControl은 Android가 알림을 게시한 뒤 `NotificationListenerService`에서 평가합니다.
게시된 알림을 취소하거나 다시 알릴 수 있지만 다른 앱의 알림을 표시 전에 차단하거나,
임의로 읽음 처리하거나, 다른 앱의 알림 채널을 직접 변경할 수는 없습니다.

## 안내형 규칙 생성

새 규칙은 최근 관찰한 앱 또는 채널을 검색해 선택하고, 취소/다시 알림/유지 동작과 선택형
시간대·반복 임계치를 고른 뒤 이름을 붙이는 안내 흐름으로 시작합니다. 일반적인 경우에는
Android 패키지명이나 채널 ID를 직접 찾을 필요가 없습니다.

취소와 다시 알림 초안은 **관찰** 모드로, 보호용 Keep 초안은 높은 우선순위의 **활성**
모드로 시작하며 저장 전에 차이를 설명합니다. 아직 알림이 오지 않은 앱은
`com.example.app` 같은 검증된 패키지명을 직접 입력할 수 있습니다. 고급 트리는 안내형
모델로 되돌릴 수 없는 구조를 만들 수 있으므로 해당 초안에서 고급 편집기 전환은 단방향입니다.
기존 복합 규칙은 항상 손실 없는 고급 트리로 엽니다.

## 활성 모드와 관찰 모드

- **활성** 규칙은 우선순위 순으로 평가하며 처음 확실히 일치한 규칙만 실제 동작을 정합니다.
- **관찰** 규칙은 별도 목록에서 독립적으로 평가합니다. 처음 일치한 규칙의 “취소될 예정”
  같은 예상 동작만 기록하며 알림이나 활성 규칙에 영향을 주지 않습니다.
- 비활성 규칙은 어느 목록에서도 평가하지 않습니다. 실제 알림 흐름에서 안전하게 시험한 뒤
  관찰 규칙을 활성 규칙으로 바꿀 수 있습니다.
- `UNKNOWN`은 일치가 아닙니다. ML·LLM·Ranking·빈도 정보가 없으면 파괴적 동작을 실행하지
  않습니다.

## 조건과 복합 논리

패키지, 제목/본문 포함, Android 카테고리, 채널 ID, 진행 중 여부, ML 라벨, 시간대, 의미
분류, 대화, 포그라운드 서비스, 중요도, 빈도를 조건으로 사용할 수 있습니다. 편집기에서
`AllOf`, `AnyOf`, `Not`을 최대 깊이 32, 전체 256노드까지 중첩하며 트리를 그대로 보존합니다.

형제 노드는 위아래로 이동할 수 있습니다. 순서는 Boolean 의미를 바꾸지 않지만 평가 순서를
바꿔 자주 실패하는 조건을 더 빨리 단락 평가하게 할 수 있습니다. 비어 있거나 잘못된 노드는
오류로 표시되며 유효한 규칙으로 저장되지 않습니다.

## 빈도 규칙

- 범위는 **패키지** 또는 **패키지 + 채널**입니다.
- 시간 창은 1~1,440분, 임계치는 2~1,000건입니다.
- 현재 평가 중인 알림도 횟수에 포함합니다.
- 리스너 연결 시 최대 최근 24시간의 내용 없는 occurrence 메타데이터를 Room에서 한 번
  읽습니다. 이후 수락한 게시 콜백은 제한된 로컬 occurrence 저장소에 먼저 반영하고,
  규칙 평가는 Room을 다시 조회하지 않고 인메모리 인덱스를 읽습니다.
- 리스너 연결 해제, 프로세스 재시작, 대기열 초과, 저장 실패가 발생하면 관측하지 못한 구간이
  생길 수 있습니다. 이 경우 각 빈도 신호는 자기 시간 창을 다시 완전히 채울 때까지
  `UNKNOWN`입니다. 1분 규칙은 연속 관측 약 1분 뒤 복구될 수 있지만 가장 긴 규칙은 최대
  24시간이 걸릴 수 있습니다. 워밍업 중에도 다른 규칙 조건은 계속 동작하며 빈도 조건은
  fail-open 처리됩니다.
- 초기화가 실패하거나 채널 범위 규칙에 채널 ID가 없으면 결과는 `UNKNOWN`입니다.

빈도 규칙은 로컬 이벤트 메타데이터가 나타내는 게시 콜백 수를 셉니다. 제목이나 본문을
집계하거나 보관하지 않습니다.

## 런타임 안전성

리스너는 알림 작업을 최대 64개 추적하고 동시에 최대 4개만 평가합니다. 같은 알림의 새 게시가
오면 대기 중인 이전 작업을 교체합니다. 규칙이나 개인정보 설정이 바뀌면 취소/다시 알림 Binder
호출 직전에 오래된 작업 권한을 무효화하며 시작 캐시가 준비되지 않으면 2초 뒤 fail-open
합니다. 과부하 또는 오래된 상태에서는 알림을 건드리지 않는 쪽을 우선합니다.

## 보호 템플릿

알람, 대화, 포그라운드 서비스, 고중요도 보호는 확인·편집 가능한 **Keep** 초안을 만듭니다.
초안 우선순위는 현재 최고값보다 100 높게 포화 계산하지만 자동 저장하지 않습니다. 활동
기록에서도 특정 앱 또는 앱+채널 Keep 초안을 만들 수 있습니다. Android/OEM 경로에서
Ranking 정보가 없으면 해당 조건은 `UNKNOWN`입니다.

## 채널 제어

활동과 일별 카드에서 정확한 Android 알림 채널 설정을 열 수 있습니다. 채널 ID가 없거나
OEM이 해당 Activity를 제공하지 않으면 해당 앱의 전체 알림 설정으로 이동합니다. 그 화면에서
사용자가 직접 채널을 무음 또는 차단해야 하며, 이것이 향후 채널 헤드업 알림을 예방하는
Android 지원 방식입니다.

## 의미 분류

앱에 포함된 로컬 의미 인코더는 알림을 다음 7개 값으로 분류합니다.

| 값 | 의미 |
|---|---|
| `MARKETING` | 홍보·판매 의도 |
| `TRANSACTIONAL` | 계정·결제·주문 등 사용자 거래 |
| `SECURITY` | 인증·사기·보안 경고 |
| `DELIVERY` | 배송 상태 |
| `SOCIAL` | 사람·소셜 상호작용 |
| `OTHER` | 나머지 명확한 의도 |
| `AMBIGUOUS` | 누락·모순·형식 오류·시간 초과·낮은 신뢰도 |

신뢰할 수 있는 인코더 결과만 활성 의미 조건을 충족할 수 있습니다. 의미 의도가 활성 승자를
바꿀 수 있을 때만 제한된 실시간 추론을 실제 동작 전에 실행합니다. 관찰에만 필요한 의미
추론은 활성 판정이 끝난 뒤 실행하며 실제 동작을 바꾸지 못합니다. `AMBIGUOUS`, 낮은 신뢰도,
시간 초과, 누락, 잘못된 출력은 사용할 수 없는 신호이며 fail-open 처리합니다.

번들 7종 의미 분류기는 기본값이 켜짐입니다. **설정 → 기기 내 의미 분석**에서 끄면 실시간과
관찰 추론 모두 모델을 호출하지 않습니다. 의미·광고 조건에 동작이 의존하는 알림은 그대로
두고, 그 밖의 알림은 나머지 규칙 신호로 처리합니다.

`IsAdvertisement(true)`는 호환성을 위해 `MARKETING`을 뜻하며 별도의 여덟 번째 클래스가
아닙니다. 사용자의 교정은 로컬 7클래스 축소 사전분포에만 반영되며 알림 내용이나 기울기를
내보내지 않습니다.

AlarmControl v0.1.0은 활성화된 호환성 프로필이 없으므로 별도로 가져온 생성 LLM을 실행하지
않습니다. 향후 검증된 프로필로 이 선택 경로를 활성화하더라도 결과는 관찰 전용입니다. 이후
로컬 교정, 통계, 추천을 보강할 수 있지만 알림 동작을 실행하거나 이미 처리한 알림을 소급해서
바꿀 수 없습니다.

## 분석, 처리 설명, 추천

규칙 분석기는 같은 실행 모드 안에서 확실히 증명할 수 있는 완전 중복, 동일 조건 shadowing,
서로 배타적인 package/category/channel 요구, Boolean 모순, `X AND NOT X`, 이중 NOT,
단일 자식 그룹만 경고합니다. 저장을 막지 않으며 임의 문자열 포함관계를 추정하지 않습니다.

선택된 활성·관찰 규칙을 합쳐 최대 128개의 트레이스 노드를 보관할 수 있습니다. 저장 항목은
조건 종류, `MATCH`/`NO_MATCH`/`UNKNOWN`, 깊이, 순서, lane뿐이며 비교값, 알림 내용,
LLM reasoning은 제외합니다.

최근 7일 로컬 SQL 집계는 다음 두 경우만 제안합니다.

- 채널 이벤트가 10건 이상이고 실제 음소거 비율이 80% 이상이면 시스템 채널 검토
- 한 패키지에서 마케팅 교정이 3회 이상이고 비율이 75% 이상이면 관찰+취소 규칙 초안

추천을 자동 저장하거나 활성화하지 않고 구조적으로 같은 기존 규칙은 제외합니다. 사용자가
닫은 추천은 안정적인 로컬 키로 기록해 다시 노출하지 않습니다.
